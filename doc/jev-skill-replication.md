# 用 Skill 复刻 Jev：能复刻"接口形状"，难复刻"校准语义"

> 结论先说：能用 skill 复刻 Jev 的"接口形状"，很难复刻它的"校准语义"。把 Jev 的效果拆成四层看会很清楚。

## 一、把 Jev 的"效果"拆成四层

| 层次 | 具体内容 | skill 能否复刻 |
| --- | --- | --- |
| **L1 接口形状** | 接收 `state` + 一组 typed questions，返回 typed answers（choice / score / noul）与概率分布，零解析 | ✅ 完全可以 |
| **L2 求值拓扑** | 一次请求内多问题并行、相互隔离；加问题几乎不增延迟；无 context-rot | ✅ 基本可以（工程手段） |
| **L3 成本/速度** | 快 ~194 倍、便宜 ~445 倍 | ⚠️ 部分可以，且官方自称是"现实收益的高端" |
| **L4 校准概率** | 说 0.8 就约 80% 正确；不确定性是可依赖的信号 | ❌ 几乎不能（这是训练目标层的属性） |

**L4 才是 Jev 的真正卖点。** 前面三层拿走之后，剩下的就是一个"很快的分类器"——而单纯分类这件事，LLM + 约束解码早就做得不错了。

## 二、L1：接口形状，skill 轻松复刻

传统 LLM 用 structured outputs / function calling / JSON mode / logit_bias 就能做出完全一样的请求-响应契约：

```json
{
  "type": "object",
  "properties": {
    "department": { "enum": ["billing", "technical", "sales"] },
    "frustration": { "type": "integer", "minimum": 0, "maximum": 2 },
    "is_urgent": { "type": "boolean" }
  },
  "required": ["department", "frustration", "is_urgent"]
}
```

事实上的 function calling / tool schema 就是一个 prompt 化的 Jev：

- **Choice** ≈ enum 字段
- **Score** ≈ 带 range 的整数
- **Noul** ≈ boolean

文档里"答案被约束在你提供的选项内，绝不会返回列表之外的值"这一条，靠**受限解码（constrained decoding）**同样能保证。

> 所以 L1 不是壁垒。

## 三、L2：并行隔离求值，也能工程化复刻

Jev 的"批量 13 问比分 13 次调用便宜 11.5 倍、快 9.6 倍"来自三点：**共享 state、并行评估、答案互不污染**。用 LLM 复刻的做法：

- **一次调用打包所有问题**（把问题写成 schema 的多个字段），而不是 N 次调用 → 省掉 N-1 次 prefill 和网络往返
- **共享 prefill / KV cache 复用**：state 只编码一次
- **并行 constrained decoding**：社区已有这些做法（第三方报道里也提到了）
- **问题间隔离**：在 schema 里平行排列，不要写成"基于上一题的答案，再判断……"

代价在于：LLM 的自回归本质是逐 token 生成，Jev 是"一次并行给出所有判断"。同样的答案，前者的 output token 数随问题数线性增长——这正是 445 倍成本差的主要来源之一。

## 四、L4：为什么校准是 skill 复刻不了的

这是核心。**校准（calibration）是训练目标层的属性，不是提示层的属性。**

### 4.1 你从 LLM 拿到的"概率"不是校准概率

三种常见做法及其问题：

| 做法 | 得到的概率 | 问题 |
| --- | --- | --- |
| 读 logprobs | token 级对数概率 | 经过 temperature / top-p 采样扭曲；RLHF 后的模型系统性过度自信；且它是"下一个 token 的概率"，不是"命题为真的概率" |
| 让模型自报"我有 90% 把握" | 自然语言数字 | 这是生成出来的文本，没有任何统计保证，纯属措辞偏好 |
| 多次采样投票（self-consistency） | 经验频率 | 成本 ×N，且测的是"采样多样性"，不是"正确答案的概率" |

Jev 的 RLCD 契约是：**模型不生成文本；返回决策和概率；概率越高，答案正确的可能性应越大。** 第三条是训练时被优化的目标——0.2 的结果就应约有 20% 发生，0.8 就应约有 80%。这需要在训练阶段用可验证的结果去校准，提示词改不出来。

### 4.2 RLHF 的失效点恰好在这一层

TypeSafe 在 AI Primer 里指出的问题，用 skill 一个都绕不过去：

- **人类偏好 ≠ 机器可信度**：RLHF 优化的是"人喜欢"，不是"可靠到能无人值守"
- **奖励谄媚（sycophancy）**：你说"我觉得是 billing"，它就更倾向说 billing
- **自信的幻觉**：语气上确定，统计上不成立
- **模式丢弃（mode dropping）**：偏好优化把概率质量压向某种风格，其他合理选项的概率被不当压低——这会直接破坏概率分布的形状，让 confidence 失去意义

### 4.3 还有一个更隐蔽的问题：context-rot 与语义串扰

Jev 的答案相互独立——`department` 的答案不会成为 `is_urgent` 的隐藏上下文。但对 LLM 来说，所有问题都在同一个注意力场里：

- 问题一多，模型的注意力会被稀释（context-rot）
- 前一个问题的措辞会泄漏到后一个问题的判断里
- 想规避就只能拆成多次调用——于是 L2 的性能优势也没了

这是一个二难：**想要隔离就得拆调用（失去 L2），想保住 L2 就得共用上下文（失去隔离与校准）。** Jev 用架构绕开了这个二难。
