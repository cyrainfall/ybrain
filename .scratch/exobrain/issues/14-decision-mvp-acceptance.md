# 14 决策：MVP 验收标准与构建顺序

Type: grilling
Status: resolved
Blocked by: 06, 07, 08, 09, 10, 11, 12, 13, 15

## Question

所有设计决策落地后，与本人对话敲定最小可用版本（MVP）的边界和施工顺序：

1. **验收清单**：逐条列出"做到什么算跑通"——例如：Android 分享一段文字 10 秒内出现在收件箱；网页剪藏一篇公众号文章正文完整；提问能基于已捕获内容回答并给出出处；新内容 5 分钟内自动生成摘要标签；
2. **构建顺序**：服务开发/部署的先后（先底座与存储 → 捕获接口 → 提炼工作进程 → 问答 → 访问与备份），每步可独立验证；
3. **毕业任务票据**：把"尚未明确"中的构建/部署雾区拆成具体任务票据挂到本地图上，此后地图进入执行阶段，直到 MVP 在服务器上跑通；
4. **明确不做**：验收清单外的内容一律推迟。

产出：验收清单 + 构建顺序 + 新毕业的任务票据。

## Answer

2026-09-06 定稿，设计阶段结束。完整清单见工件 [prototypes/mvp-acceptance.md](../prototypes/mvp-acceptance.md)。

**验收清单**：六组共 20 条实测项——A 访问组网（3）、B 捕获（5，含断网补发）、C 自动提炼（5，含停服补处理、失败标红）、D 问答（3，含"无依据明说"、归档可命中）、E Mac 浏览与备份（3，含七步恢复演练）、F 资源稳定（72 小时不 OOM）。

**构建顺序**（11 张任务票据，已挂地图）：16 服务器初始化 → 17 fork 骨架与 CI/ACR → 18 headscale 组网 / 19 捕获接口（19 又分出 20 浏览器扩展、21 安卓配置、22 数据层）→ 23 知识工具 → 24 提炼队列与周复盘 → 25 Git/Gitee 备份 → 26 端到端验收与恢复演练。

**明确不做**：微信读书同步（MVP 后第一增量）、企业微信/推送渠道、PDF 长文档、多用户/限流、域名 TLS、存量迁移、本地模型。

**构建原则**：每步可独立验证；ybrain 代码隔离在 `packages/ybrain/` 遵守 fork 合并纪律；原型工件（数据模型、检索参数、接口契约、提炼流程、备份步骤）直接作为施工依据。
